2. **精读 vLLM Kimi K3 `eh_proj` 优化（[PR #53942](https://github.com/vllm-project/vllm/pull/53942)），将其作为你"低延迟 GEMM + 小 batch 优化"方向的 kernel 级参考。** 该 PR 通过启用 m=1 和 m=2 低延迟 GEMM 模式，实现 12.9%~25.2% 内核性能提升，直接关联你关注的 CUDA kernel 优化与推理延迟。建议你阅读其 CuTe 内核实现，理解小 batch 下如何通过调整 tile 形状和流水线深度来降低启动开销。然后在本地 vLLM 中，使用类似 MLA 架构的模型（如 Kimi K3 或 Qwen3-MLA）对比"默认 GEMM"与"低延迟模式"在 decode 阶段单请求延迟和吞吐上的差异，并评估该优化是否可迁移到你的自定义 kernel。

3. **关注 SGLang sm_107 all-reduce 调优（[PR #36397](https://github.com/sgl-project/sglang/pull/36397)）与 Rubin 支持（[PR #36233](https://github.com/sgl-project/sglang/pull/36233)），将其作为你"Blackwell 之后新硬件推理路径"的早期验证点。** 这两个 PR 分别针对 sm_107 架构调优自定义 all-reduce v2 和添加 CUDA 13.4 容器支持 Rubin，直接命中你关注的"新硬件上的推理部署路径"。建议你阅读 all-reduce 调优的启发式配置逻辑，理解不同消息大小下如何选择最优算法。然后结合 Rubin 容器，在本地（若有 Rubin 环境）或通过模拟，对比"自定义 all-reduce v2"与"NCCL"在多种消息大小下的延迟和带宽利用率，重点关注该调优对 MoE dispatch 中专家并行通信的实际收益。

4. **结合今日 llm-compressor 的 GPTQ 回退汇总（[PR #3098](https://github.com/vllm-project/llm-compressor/pull/3098)）与 imatrix fouroversix（[PR #3076](https://github.com/vllm-project/llm-compressor/pull/3076)），将其作为你"量化正确性与精度保障"方向的验证点。** 前者修复了 GPTQ 量化中 Hessian 求逆失败时静默回退到 RTN 的问题，后者为 nvfp4 默认引入 fouroversix 观察器，直接关联你关注的 FP8/FP4 量化与 MoE 模型。建议你阅读回退汇总逻辑，理解哪些模块容易触发 Hessian 求逆失败，以及回退对最终模型精度的影响。然后在本地 llm-compressor 中，使用 MoE 模型（如 Mixtral-8x7B）对比"修复前（静默回退）"与"修复后（显式警告）"在量化后困惑度和端到端延迟上的差异，并评估 fouroversix 观察器在 nvfp4 下对全局缩放精度的实际提升。
