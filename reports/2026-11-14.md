2. **跟进 sglang [[PR #50364](https://github.com/sgl-project/sglang/pull/50364)](https://github.com/sgl-project/sglang/pull/50364)（masked per_token_group_quant 支持 dense SiLU+mul 融合）并把它作为"MoE 量化路径 dense/masked 布局一致性"的检查点**：这条的价值不在融合本身，而在它暴露了 masked 布局此前直接抛 ValueError、而底层 `QuantTrait::run` 早已实现该模式——说明 masked 与 dense 两条量化路径长期存在能力不对齐，这正是 MoE 场景下量化 kernel 选型容易踩的坑。可执行动作：先读 diff 确认 masked 路径接入融合后，per-token-group 的 group 边界是否仍按 masked 后的有效 token 划分，重点核对 padding token 是否被计入 group 统计——若计入，group scale 会被无效 token 稀释，量化误差在短序列 MoE 上放大。再核对融合后的 SiLU+mul 是在量化前还是量化后执行：若在量化前，激活值分布会因融合而改变，需确认 group scale 的统计口径与 dense 路径完全一致，否则同一模型在 dense/masked 两种布局下输出不可比。最后在本地用 MoE 模型（专家数不整除 TP 的场景）分别走 dense 与 masked 量化路径，对比同一输入的输出差异与 per-group scale 分布，确认两条路径可互换。

3. **把 flashinfer [[PR #9296](https://github.com/flashinfer-ai/flashinfer/pull/9296)](https://github.com/flashinfer-ai/flashinfer/pull/9296)（decode benchmark 尊重投机掩码，排除不兼容的因果 TRTLLM 后端与 SM10x 原生自动路由）当作"投机解码基准可信度"的校准动作**：这条修的是基准测试本身——此前 decode benchmark 未按投机掩码过滤后端，会把不支持投机解码的后端纳入对比，导致你此前读到的 decode 吞吐数字可能混入了非投机路径的结果。可执行动作：先读 diff 确认掩码过滤发生在 setup、执行、参考选择三个阶段的哪几处，重点核对"参考选择"阶段被排除的后端是否也影响了正确性参考的选取——若参考实现本身被掩码排除，基准的数值正确性校验会退化。再核对 SM10x 原生自动路由被排除的具体条件：确认是这些路由在 full-mask 投机下不支持，还是仅未被验证；若是后者，可考虑在本地补一条
