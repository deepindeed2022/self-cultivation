## 今日研究方向建议

1. **精读 SGLang [[Roadmap] Issue #21788 Prefill Context Parallelism (2026 Q3)](https://github.com/sgl-project/sglang/issues/21788)，把它作为你"disaggregated prefill/decode + 长上下文 prefill 并行"方向的路线图锚点。** 该 roadmap 明确列出 MLA/SWA 模型支持、KV cache 分片、all-to-all 通信优化三项已完成/待办，正好命中你关注的分布式 KVCache 与 prefill/decode 分离。建议先读其 KV cache 分片方案（按 head 还是按 token 切、与 MLA 压缩潜向量的交互），确认分片后 all-to-all 的通信量与 CP 度数是否呈线性；再对照你当前的 PD 部署，判断 prefill CP 能否与现有 prefix-caching 共存（分片后 prefix 命中判定是否仍按全局 block 索引）。注意与 9-24 已推送的 #41179（DP speculative coordination）区分：那条是调度正确性，这条是 prefill 并行架构。

2. **跟进 vLLM [[[PR #59017](https://github.com/vllm-project/vllm/pull/59017)] Keep in-flight requests on the same DP engine](https://github.com/vllm-project/vllm/pull/59017)，把它作为你"DP 路由 + continuous batching 流式请求一致性"方向的排查点。** 该修复在负载均衡前检查 `reqs_in_flight`，让已分配引擎的流式请求复用原引擎——直接关联你关注的 continuous batching 与 DP 部署。建议先读其判定逻辑：`reqs_in_flight` 的更新时机与流式请求跨 chunk 的边界，确认在 prefix-caching 命中导致请求被重路由时是否仍会漂移；然后在本地 vLLM 上跑 DP>1 + 流式 + prefix caching 场景，对比修复前后同一请求的引擎归属与首 token 延迟抖动，判断你当前 DP 前端是否落在同一 bug 窗口。

3. **精读 FlashInfer [[[PR #5644](https://github.com/flashinfer-ai/flashinfer/pull/5644)] cake_sparse_mla round-4 DSv4 sparse-MLA Cake programs for SM100/SM103](https://github.com/flashinfer-ai/flashinfer/pull/5644)，把它作为你"Blackwell 稀疏 MLA 解码 + FP8/BF16 混合精度"方向的直接切入点。** 该轮通过重排 K gather、加深 K/V 别名环、FA4 式惰性 softmax 重缩放提升 decode/prefill 吞吐，正好命中你关注的 FP8 低精度推理与 Blackwell 部署。建议先读其惰性 softmax 重缩放的触发条件（何时跳过 rescale、与 sparse 索引的耦合），确认在 page-64 边界处 K gather 重排是否引入额外依赖；然后在本地 SM100/SM103 上用 DeepSeek-V4 或同类稀疏 MLA 模型，对比 round-3/round-4 在 decode 延迟、SM 占用率与 logits 一致性上的差异。可与 9-27 已推送的 #5590（KDA/MLA 投影 GEMM）对照，判断投影侧与注意力侧的优化是否共用同一套 scale 元数据。

4. **跟进 NVIDIA Model-Optimizer [[[PR #2273](https://github.com/NVIDIA/Model-Optimizer/pull/2273)] Compose GEMM and KV-cache AutoQuant workflows](https://github.com/NVIDIA/Model-Optimizer/pull/2273)，把它作为你"FP8/NVFP4 量化 + KV cache 混合精度"方向的工具链入口。** 该 PR 组合 GEMM 量化与 KV-cache AutoQuant，支持 FP8/NVFP4 与混合 KV 量化并统一导出，正好命中你关注的量化与 KV Cache 管理。建议先读其 KV-cache AutoQuant 的 scale 粒度（per-token/per-head/per-block）与导出格式，确认导出的量化 checkpoint 能否直接被 vLLM/SGLang 的 KV cache 加载路径消费；然后在本地用 BERT 或小规模 LLM 跑一遍 GEMM+KV 联合量化，对比仅 GEMM 量化在显存、decode 延迟
