1. **精读 vLLM Issue #40069（TurboQuant/HIGGS Attention follow-ups），把它作为你“KV cache 低精度存储 + 注意力后端”方向的直接切入点。** 该追踪 issue 已把 FA3/FA4 支持与长上下文精度评测做完，但混合注意力、MLA 支持与逐层敏感度扫描仍待完成——正好命中你关注的 KV cache 量化与 MLA 后端。建议先读 issue 中逐层敏感度扫描的待办描述，确认它打算用何种指标（per-layer 输出误差还是 end-to-end logprob 偏差）来判定哪些层可以降精度；然后在本地 vLLM 中开启 TurboQuant/HIGGS，用长上下文模型对比逐层敏感度扫描前后在 KV 显存占用、decode 延迟和输出数值一致性上的差异，判断该后端能否纳入你的低精度 KV 方案。

2. **跟进 vLLM Issue #56370（`VLLM_BATCH_INVARIANT=1` + 序列并行/异步 TP 破坏批次不变性），把它作为你“分布式推理 + 投机解码数值一致性”方向的可靠性排查点。** 该 bug 报告同一请求因批次组成不同而产生不同 logprobs 甚至不同 token，直接关联你关注的 TP/SP 分布式推理与投机解码（验证阶段对 logprob 一致性极度敏感）。建议阅读 issue 中序列并行下 all-reduce 归约顺序与 batch-invariant kernel 的冲突分析，确认破坏不变性的是归约顺序还是 kernel 选择；然后在本地 vLLM 中开启 `VLLM_BATCH_INVARIANT=1` 与 SP/async TP，用 EAGLE3 或 MTP 跑不同 batch 组成，对比 logprob 偏差与 accept rate 波动，确认你的生产配置是否踩到该问题。

3. **精读 TensorRT-LLM [PR #19296](https://github.com/NVIDIA/TensorRT-LLM/pull/19296)（SA/DFlash/PARD 验证后恢复语法状态），把它作为你“投机解码 + 引导/结构化生成”方向的正确性修复参考。** 该 PR 为投机验证后新增引导解码接受追踪与拒绝 token 回滚，直接命中你关注的 speculative decoding 与多轮对话输出约束。建议阅读其“接受追踪 + 拒绝回滚”的状态机设计，重点确认在部分接受（前缀接受、后缀拒绝）时语法状态如何回退到正确位置；然后在本地 TensorRT-LLM 中用带 grammar 约束的投机解码跑一组，对比修复前后在拒绝 token 后的语法合法性、accept rate 和端到端延迟上的差异，评估该修复是否影响你当前的投机解码配置。

4. **关注 lightseekorg/tokenspeed [PR #1622](https://github.com/lightseekorg/tokenspeed/pull/1622)（gfx1250 MXFP4 MoE 操作数加载融合 partial TDM），把它作为你“MoE dispatch + FP4 低精度 kernel”方向的实测入口。** 该 PR 将两个操作数加载融合为一次 TDM 操作，直接关联你关注的 MoE dispatch 与 FP4 推理。建议阅读其 partial_tdm 选项对操作数布局与 TDM 描述符的要求，确认融合后是否改变了权重/激活的 swizzle 假设；然后在本地复现 gfx1250 MXFP4 MoE 内核，对比开启 partial_tdm 前后在 MoE 层延迟、TDM 事务数和输出数值一致性上的表现，作为你评估 FP4 MoE kernel 优化空间的基线。

5. **精读 NVIDIA/Model-Optimizer [PR #2414](https://github.com/NVIDIA/Model-Optimizer/pull/2414)（修复 vLLM 混合注意力/Mamba 模型 fakequant 校准），把它作为你“低精度量化 + 混合注意力 KV cache”方向的校准排查点。** 该修复为每个 KV-cache group 分配非空 scratch block 并适配 vLLM 0.28 请求生命周期，此前空 block table 导致 Mamba 状态落到 null block、校准激活变 NaN——正好命中你关注的量化校准与 KV cache 管理。建议阅读其按 KV-cache group 分配 scratch block 的逻辑，确认混合注意力模型下 Mamba 状态与注意力 KV 的 block 分配如何解耦；然后在本地 vLLM 0.
