## 今日研究方向建议

1. **精读 SGLang [[PR #43993](https://github.com/sgl-project/sglang/pull/43993)](https://github.com/sgl-project/sglang/pull/43993)（DSV4.1 在 0 行 DP-idle batch 上跳过 Mega mHC 融合）**，这是你"MoE dispatch + DP attention + 分布式推理"交叉处今日最直接的入口。建议先读 diff 中判定"0 行 batch"的条件与跳过融合后的 fallback 路径：确认它是在 host 端按 `num_tokens==0` 提前返回，还是仍在 kernel 内走一条非融合分支；然后对照今日 [commit #43812](https://github.com/sgl-project/sglang/commit/43812)（DSV4.1 decoder SWA bounded replay with CUDA DP attention）中 DP attention 在 idle rank 上的重放语义，判断两者是否共享同一套"空 batch 不参与集合通信"的假设——若共享，则你后续做 EP/DP 混合并行时可以把"0 行 batch 短路"作为通用前置条件写进调度层。

2. **跟进 vLLM [[PR #60908](https://github.com/vllm-project/vllm/pull/60908)](https://github.com/vllm-project/vllm/pull/60908)（FA4 设为 AttentionCGSupport.ALWAYS）**，这是你"continuous batching + cudagraph + 混合 prefill/decode"方向今日最值得实测的改动。建议先读 diff 中 `AttentionCGSupport.ALWAYS` 的判定条件，确认它是否要求同一 token 数下 batch 布局可任意变化（含 prefill+decode 混排）而无需重捕获；然后在本地 FA4 后端上构造"固定总 token 数、prefill/decode 比例从 8:0 扫到 0:8"的批次序列，对比 ALWAYS 与旧策略下的图捕获次数与端到端延迟，重点看混合批次是否真的复用了同一张 FULL cudagraph——这直接决定你能否把 cudagraph 的收益从纯 decode 扩展到 chunked prefill 场景。

3. **精读 FlashInfer [[PR #6138](https://github.com/flashinfer-ai/flashinfer/pull/6138)](https://github.com/flashinfer-ai/flashinfer/pull/6138)（pinned NVFP4 decode 中 tcgen05.mma 前对通用 SMEM 写入补 fence.proxy.async）**，把它作为你"Blackwell FP4 推理 + kernel 正确性"方向的直接切入点。该修复针对 GR100/B200 上重复调用结果不一致，正好命中你关注的 FP4 与新硬件部署。建议先读 diff 中 fence 插入的位置：确认它保护的是 tcgen05.mma 读取的 A/B operand 还是 accumulator 初始化路径，以及为何普通 SMEM store 与 tcgen05 的 async proxy 之间存在可见性缺口；然后对照今日 [[PR #6441](https://github.com/flashinfer-ai/flashinfer/pull/6441)](https://github.com/flashinfer-ai/flashinfer/pull/6441)（concat_mla_kv_quant_fp8 的 4+2 head-group plan）中同一 warp 内多 head 的 SMEM 复用方式，判断该 head-group 规划是否也会触发同类 proxy 可见性问题——若会，则你在自写 FP4 MLA kernel 时需把 fence 位置与 head 分组策略一起设计。

4. **跟进 SGLang [[PR #32947](https://github.com/sgl-project/sglang/pull/32947)](https://github.com/sgl-project/sglang/pull/32947)（GLM5.2 DSA Indexer Fallback）**，这是你"FP8 量化 + 稀疏注意力 indexer + 硬件可移植性"方向今日最具体的落地素材。建议先读 diff 中 `SGLANG_FP8_PAGED_MQA_LOGITS_TORCH` 环境变量生效的判定路径：确认 fallback 是替换了整个 MQA-logits kernel 还是仅替换了 DeepGEMM 缺失时的 GEMM 后端，以及 FP8 scale 布局在 torch fallback 与 DeepGEMM 路径下是否一致；然后在无 DeepGEMM 的机器上跑一遍 GLM5.2 的 DSA indexer，逐 token 对比 fallback
