## 今日研究方向建议

1. **精读 vLLM [Issue #40846](https://github.com/vllm-project/vllm/issues/40846)（RFC: Rust front-end，用 Rust 替代 Python asyncio 事件循环以解 CPU 侧高并发瓶颈）**：这是今日唯一直接落在"推理引擎 CPU 侧调度瓶颈"的架构级条目，与你关注的 continuous batching / 高并发 serving 主线直接相关，且与今日 SGLang #47114（Rust server 启动指标缺失）形成"Rust 前端在两大引擎同时推进"的横向对照。可执行动作：先读 RFC 中"CPU 侧瓶颈"的量化依据——确认瓶颈是在 tokenize/detokenize、请求调度循环、还是 asyncio 与 CUDA graph 提交之间的 GIL 争用，这决定 Rust 前端是替换整个调度器还是只替换 I/O 层；重点看它是否保留 Python 侧 `Scheduler` 语义（若 Rust 侧重写调度，continuous batching 的抢占/重算逻辑需重新验证）。然后在本地构造高并发短请求场景（如 512 并发、输出 8 token），对比 Python 前端与 Rust 前端在 CPU 占用与 TPOT 上的差异，并测量 Python 侧事件循环占端到端延迟的比例——若占比 <10%，说明该 RFC 的收益主要在超大规模并发而非你当前的单机多卡场景，可降优先级。

2. **跟进 FlashInfer [[PR #7779](https://github.com/flashinfer-ai/flashinfer/pull/7779)](https://github.com/flashinfer-ai/flashinfer/pull/7779)（sm_103a 上 dense FP8 64 头 MQA 的 full-block qle2048 kvsplit 路由在 K≤8192 时复用 partial-block 程序）**：这是今日"FP8 attention kernel + 新硬件路由阈值"最具体的一条，与你 10-25 跟进的 Cake NVFP4 attention（SM100/SM103）同属 FlashInfer 在 Blackwell 系上的低精度 attention 后端，可形成"NVFP4 decode → FP8 MQA prefill/decode 路由"的对照。可执行动作：先读 diff 确认 K=8192 这个阈值的来源——是 partial-block 程序在 K>8192 时寄存器/共享内存溢出，还是 kvsplit 的 split 数超过 SM 数导致负载不均；重点核对 64 头 MQA 下 KV head 数为 1 时 kvsplit 的切分维度（沿 K 切还是沿 batch 切），以及 full-block 与 partial-block 两条程序在边界 K 上的数值是否逐位一致。然后在本地 sm_103a 上构造 K=4096/8192/16384 三档，对比开关前后延迟与输出 logits 偏差，重点验证阈值附近是否存在性能断崖——若存在，说明阈值应随 batch 动态调整而非固定常量。

3. **精读 SGLang [[PR #34031](https://github.com/sgl-project/sglang/pull/34031)](https://github.com/sgl-project/sglang/pull/34031)（spec: 将 ragged-verify 布局统一为 ForwardBatch 一等字段，删除 SpecInput 类级载体）**：这是今日投机采样路径唯一的结构性重构，虽标注"无行为变化"，但 ragged-verify 布局的承载方式直接决定后续 spec decode 的 CUDA graph 兼容性与 kernel 入参形态，与你关注的 speculative decoding 主线相关。可执行动作：先读 diff 确认 `ForwardBatch` 新增字段的 padding 语义——ragged-verify 下不同请求的 verify 长度不同，统一到 ForwardBatch 后是否仍保留 per-request 的 token 偏移表，还是改为全局扁平化；重点看删除 `SpecInput` 后，draft model 与 target model 之间的 hidden state 传递是否改走 ForwardBatch 的哪个字段（若走新增字段，需确认其 dtype 与 layout 是否与 target model 的 attention kernel 期望一致）。然后在本地开启 spec decode（EAGLE/Medusa 任一），对比重构前后同一 prompt 的接受率与输出 logits 偏差，重点验证 ragged-verify
